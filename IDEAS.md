22. **Close the review loop with Morten** `[org]` `[eng]`
   On 07.08 Morten delivered four images in one pull request. The review on 08.08 asked for a change to the human figures, and the pull request was closed an hour later. He *did* react — he regenerated all four images and wrote his reasoning into the description — but only because Christian told him about the review by hand, and by then the request was closed, so the rework landed on a branch nobody opens. Acting on a review is not the gap; being told by hand is the whole procedure today, and that is the next step. Two things are missing, and they are one design. **He has no structured way to learn that a review happened or that a request is closed:** his triggers are the Friday schedule and messages in `#crew`, so listing his own pull requests and their reviews at the start of every run costs nothing new, while an event-driven trigger depends on what inbound hook Abundly offers. **And the delivery is too coarse to review:** four images in one commit can only be accepted or rejected together, so a single objection kills three pictures that were fine — one image per pull request would make a correction to one imageprompt testable on its own. Whatever gets built keeps the repo as the source of truth: a review comment is the same side channel as Slack, so a change that is not in the imageprompt gets named rather than followed, and a rework needs a cap so that reject → regenerate cannot loop. *Why now: this is the concrete blocker under the open question of 20260810 — what the flow has to look like for Morten to take over a whole post. (From the 20260810 session.)*
   **Rescoped 2026-08-11, and promoted from next step to prerequisite.** Half of it is already answered by the drafting design: one pull request per post was Christian's own spec, so a single objection can no longer kill three pictures that were fine. What remains is the review half, and it now gates the drafting stage on 21.08 — a first draft needs a revision round, and Morten cannot see that a review happened. **Harvest ships without it**, because duplication there is prevented by cheaper means: the watermark only moves when Christian merges, and there is one open harvest pull request at a time, so an unmerged harvest keeps its own entries in scope instead of proposing them again somewhere new. The minimum version of the review half needs no new capability — list his own open pull requests and their reviews at the start of every run; his token already carries Pull requests read & write. Plus a rework cap, and the rule that a correction living only in a review comment is the same side channel Slack was on 21.07: if it generalizes it belongs in `VOICE.md`, otherwise Christian makes it in the draft himself.
   **Built 2026-08-24**, in the form described above and no larger. Every run now starts with a *Friday Review Workflow*: list his own open pull requests and the reviews on them, act on a requested change in the workflow the request belongs to, and push the rework to the same branch and the same pull request. Three rules travel with it — a pull request closed without merging is a full stop (no push, no reopen, no replacement), a correction that lives only in a review comment is the same side channel Slack was on 21.07 and gets named rather than followed, and reworks are capped at two per post so reject-and-regenerate cannot loop. The delivery granularity was fixed in the same pass: one pull request per post rather than one per day, which is the half of this item that 12.08 had answered on paper only and never carried into the image job. **Still open, and deliberately:** an event-driven trigger, which depends on an inbound hook Abundly may not offer, so a review can sit unseen until his next run — acceptable at a weekly rhythm. And Morten still has no way to contradict a review rather than work through it; that is the open question of 20260810 and not a tooling problem.

23. **The queue is one file two members write to** `[org]` `[eng]`
   Pull request #10 arrived CONFLICTING on 2026-09-04, and nobody had done anything wrong. Morten branched at 08:08 and flipped B9's status cell to `drafted` — the one status edge that is his (#A48). Christian and Claude edited `REPERTOIRE.md` three times over the same day, one of those flips putting B8 on `posted`. B8 and B9 are neighbouring table rows, so git could not merge two changes that have nothing to do with each other. **The conflict is a property of the storage, not of the collaboration:** the queue is a single markdown table, and adjacency in it is enough. Every drafting pull request touches that file, so this recurs on any week where the queue is worked on between his Friday run and the merge.
   What lifts it above a nuisance is that **he cannot see it.** The review loop lists his open pull requests and the reviews on them, not their merge state, and no workflow step resolves a conflict. A blocked request sits looking finished until a human opens it — and his rework cap and his "a closed request is a full stop" rule both assume the request is otherwise healthy.
   Three directions, none decided. **Have his run merge `main` into his own open branches first** — mechanical, no judgement, his token allows it, and it is one step in a workflow he already runs. **Report mergeability in the Friday report** — does not fix anything, makes it visible the same day, costs nothing. **Take the status out of the shared table**, so two writers stop sharing lines: the real fix and the expensive one, since a hundred references hang on that table and `REPERTOIRE.md` is also what the population rule for the statistics now points at. The fourth direction — taking the `idea → drafted` edge back off him — would also end it and is the one to avoid: that edge was given to him on 30.08 precisely because it is the one status he can observe as his own fact.
   *Why now: it blocks the weekly flow, it will come back, and the cheapest of the three is a single step in an existing workflow.* (From the 20260904 session.)
